Finding 1 — An open reset form can delete a different webinar’s counts

- Severity: Blocking
- Location: src/app/report/page.tsx:247, src/app/report/reset/route.ts:93, src/lib/webinar/report-store.ts:201 — Start again for a new webinar
- Issue: The form submits only the password. The server selects the campaign to delete from its current CAMPAIGN.id, with no check that it matches the webinar displayed when the form opened.
- Failure scenario: A team member leaves webinar A’s report open. The site switches to webinar B under the documented next-webinar procedure and B starts receiving registrations. Submitting the still-open form with the correct password deletes B’s visits and registrations, although the team member confirmed the reset on A’s report.
- Suggested fix: Include the displayed campaign ID in the form. Before calling the reset RPC, require it to match the current server-side ID. A missing or stale ID should require a refresh and delete nothing. Cover the campaign switch with a test.
- Confidence: High.

Finding 2 — The destructive E2E test does not verify which database it will reset

- Severity: Blocking
- Location: tests/e2e/webinar/report-page.spec.ts:278 and :1311 — signed-in report tests and the real reset
- Issue: testPassword() checks the password is present and rejects the canonical Production hostname. A permitted localhost server can still use Production Supabase credentials. The spec documents that the local server must use the test database, but it proceeds to deletion without establishing that fact.
- Failure scenario: A local server uses the test report password and points its Supabase client at unretire-prod. Sign-in succeeds. The reset test submits the form, erases the live campaign and can pass precisely because the live counts became zero.
- Suggested fix: Run the real reset only against a target verified to use unretire-test. Where that binding cannot be established, use a stub for the destructive case. Keep the real end-to-end assertion on the verified Preview.
- Confidence: High. This follows from the target check and reset call. Neither reviewed Preview run showed a wrong-target deletion.

Finding 3 — An unrelated website can record visits without opening the sign-up page

- Severity: Blocking
- Location: src/app/api/conversation/arrival/route.ts:73 — public arrival counter
- Issue: The handler parses the body as JSON regardless of its declared media type and accepts requests from foreign origins. A browser can therefore submit a cross-site plain-text request that records a valid source. Blocking access to the response does not prevent the database write.
- Failure scenario: Visitors to an unrelated page are counted as webinar arrivals even though they never opened /conversation. Each visitor can remain within the per-address limit while the selected platform’s visits rise and its reported conversion falls.
- Suggested fix: Require application/json for the arrival body and reject an explicitly cross-site browser request before recording it. Add a refusal test that checks the store receives no call. The shipped counter already sends same-origin JSON.
- Confidence: High.

Finding 4 — A new tab can inherit the previous tab’s visit and source

- Severity: Should-fix. Deferrable if the owner accepts the attribution limitation and the runbook describes it.
- Location: src/app/conversation/ArrivalCounter.tsx:39, src/app/conversation/tab-source.ts:42 — per-tab visit counting and sign-up attribution
- Issue: A new tab opened with an opener can inherit a copy of its opener’s sessionStorage. The counter treats the copied source as proof that this new tab already sent its own visit.

- Confidence: High.
