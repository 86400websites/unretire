`pull_request` trigger is the flaky one and `deployment_status` is authoritative. Here it happened the other way
round: `deployment_status` went red while `pull_request` was green. The lesson generalises rather than
reverses — the artefact belongs to the **protection state at the moment of the run**, not to the trigger, so
neither trigger is inherently trustworthy on its own. What settles it is a second run at the same SHA and the
failure text.

**The failed run was re-run from the Actions tab rather than argued away on paper, and attempt 2 passed
235/235 (1.6 m)** on the same commit, the same Preview and byte-identical code — nothing was changed between
the two attempts. A red that disappears on re-run with no edit is transient by definition. PR #32's checks are
now all green and its mergeable state is `clean`.

That leaves one honest residual for the reader: this artefact can strike **either** trigger, so a single green
run is weaker evidence than this project's records have historically implied. The cheap mitigation, if it keeps
recurring, is to have the workflow detect the protection page explicitly and fail with a named error instead of
an assertion mismatch, so nobody has to diagnose it from a diff of expectations again. Filed as a backlog row.
