# Sprint Record — S4.4 — Auth Boundary

Branch `claude/s4.4-auth-boundary`, from `master` `d725aea`.

## Outcome

Closes Known issues **38**, **41**, **42**, and settles **14** as a recorded decision. Issue 38 was the last launch blocker outside S4.5, so **only 3 remain: 3, 5 and 46**.

## 38 — the open redirect *(launch-blocking)*

`src/app/auth/confirm/route.ts` guarded its `next` parameter with `startsWith("/")`, which reads like a same-origin check and is not one. `//evil.example` starts with a slash, and `new URL("//evil.example", base)` is protocol-relative — it resolves to a different site. A leading backslash does the same, because the WHATWG parser rewrites `\` to `/`.

That made the single link in every account e-mail an open redirect: the victim clicks a genuine link on the real domain, arrives authenticated, and is bounced to an attacker's page with every visible detail up to that point legitimate.

**Measured against the old guard: 6 of 11 hostile inputs escaped** to `https://evil.example`.

Fixed by resolving the candidate and comparing origins, then returning a path so the redirect value cannot carry an origin at all. Extracted to `src/lib/auth/safe-redirect.ts`. Satisfies **I5**.

## 41 — shared Stripe account

Sessions are stamped `metadata.app = "unretire"`; the webhook ignores events naming another application. Events with no `app` key still fall through, so pre-existing sessions are not stranded.

It also closes a retry loop **S3.1 introduced**: making a failed write return 500 was right for transient errors, but a foreign event whose `supabase_user_id` is not a user of this project fails the `auth.users` foreign key — permanent, and Stripe would have redelivered it for days. That case is now acknowledged.

## 42 — host-header injection

`safeOrigin()` (`src/lib/auth/safe-origin.ts`) validates the host before any URL is built from it, at both sites: `getOrigin()` in `auth/actions.ts`, which decides the link inside every password-reset e-mail, and the Origin handling in `/api/checkout`.

**Additive by design** — every host this project legitimately runs on is allow-listed, so real traffic is unchanged; only a host that is none of ours is refused. The Vercel pattern requires the `-86400-s-projects` team suffix: without it, `unretire-evil.vercel.app` is a name any stranger could claim, which the spec asserts. A forged `x-forwarded-proto` can no longer downgrade a real host to http.

## 14 — fail-open middleware: ACCEPTED (D-30)

Not a hole. The middleware is not an access control — it only refreshes the session cookie — and every protected surface authorises itself, verified route by route. An unrefreshed request still meets a gate that denies, and an expired token makes `getUser()` return null there, so the system **fails closed where access is decided**. Failing the middleware closed would return 500 on every route, public pages included, for no security gain. Revisit condition recorded in D-30 and in the file.

## On the tests

Both guards are asserted **directly**, not through a flow, and that is deliberate. `/auth/confirm` only consults `next` after a token exchange succeeds, so an end-to-end attempt with a bogus token never reaches the branch under test and would pass identically before and after the fix — the fifth would-be vacuous test in this project. Each spec is **verified to fail against the old implementation**.

The hostile inputs are built with `String.fromCharCode(92)`. Two earlier drafts lost their backslashes — first to shell quoting, then to TypeScript reading `"\e"` as `"e"` — and each time the attack string silently became an ordinary same-origin path while the test still passed green.

Both directions are asserted throughout: `//evil.example@www.unretireproject.com` is genuinely same-origin (attacker domain as userinfo, our host) and must still be allowed, one backslash from the hostile case; and the real production hosts must still be accepted, so a guard that rejected everything cannot pass.
