   shape). **Two facts no document records:** `status` admits a third value, `expired` (§5.1 lists two; the code
   writes only the first two), and **there is no index on `stripe_subscription_id`** (§5.1 expects one). Neither is

6. **P3 and P13 need a delivered email, and only the owner has an inbox — and the link's *host* is not the proof.**
   Under Supabase's default `{{ .ConfirmationURL }}` templates the link is `https://<ref>.supabase.co/auth/v1/verify?
   …&redirect_to=<origin>/auth/confirm…`, so its own host is the Supabase project, never the Preview. The proof is the
   **origin the link resolves to**: the owner clicks it and reports the origin in the address bar of the page it lands
   on (a 404 on `/unretire/reset-password`, or `/login?error=confirmation_failed`, is expected — Known issue 2;

   project's template is `{{ .SiteURL }}`/`{{ .TokenHash }}`-based instead, the link ignores the app's `redirectTo`
   and lands on that project's Site URL (`http://localhost:3000` for `unretire-test`) — a P3 FAIL by construction
   whose remedy is an owner dashboard template change, never an app change; the plan carries that branch. Two specs
   request one email each on the Preview (the P2 signup — a confirmation if "Confirm email" is ON — and a password
   reset for the signed-in fixture, sent regardless); P13's email half is the same read on a reset the owner requests

   limit is project-wide and summed across signup and recovery, and `requestPasswordReset()` swallows the Supabase
   error and returns the same message either way — so the reset spec going green is **not** evidence a mail was sent;
   after every run the builder reads `unretire-test`'s auth logs read-only (`supabase-test` `query_logs`, service
   `auth`) and records `sent` or `over_email_send_rate_limit` per request (status + error code only). A rate-limited
   send is an environment limit (§6 C7), re-dispatched at the same head after the hour, never a defect.

## A. Diagnosis

Isolation is configured (S2.2), reachable (MCP) and observable (S2.3), but **every claim of "Preview equals
Production" is still a dashboard reading** — `unretire-test` is an empty database of unknown shape, the auth toggles
that fork `register()` are unrecorded, and no Preview payment has ever been delivered. This sprint replicates the
definition (captured DDL, applied test-first under authorisation), records the auth-settings parity from both
dashboards, and then **proves** with the S2.3 harness that a Preview signup, a sandbox payment and an email capture each
land where they should and nowhere else — closing P2–P6, P8–P10, P12 (re-affirmed) and P13, and writing down the
irreducible gaps with the Production smoke that covers each. S5.1's suite may not start before this table is green
(§8's gate).
