## Outcome — in progress (2026-09-03)

### Bug 2 — course worksheet download — FIXED (high confidence)

**Root cause.** `src/app/api/course-worksheet/route.ts` set
`Content-Disposition: inline; filename="Module 1 — Deliverable Worksheet.pdf"`. Every approved worksheet name
carries an **em-dash (U+2014)**. The web `Headers` constructor throws `TypeError: Cannot convert argument to a
ByteString because the character … has a value of 8212 which is greater than 255`, and `new NextResponse(bytes,
{headers})` is built **outside** the route's try/catch — so the whole GET handler threw and Next answered **500**
("unable to handle this request"). The `/api/book-download` route was immune only because it builds an
ASCII-only filename first, which is why Premium book downloads (AC-015) always worked. Confirmed with a Node
repro of the web `Headers` constructor.

**Why the launch gate missed it.** Every worksheet spec (AC-011, AC-012) asserted only the **denied** paths (403
for anonymous and for a signed-in non-buyer). Nothing ever fetched a worksheet as an **entitled** member, so the
crashing success line was never executed.

**Fix.** A local `contentDisposition()` helper emits RFC 6266's two forms — an ASCII-only `filename=` plus a
UTF-8 `filename*=` carrying the real name — so no byte > 255 reaches the header and modern browsers still show
the em-dash name. New regression test: `paid-content.spec.ts` now downloads all four worksheets as the **course**
fixture and asserts 200 + `application/pdf` + a non-empty body. It fails on the old code and passes on the new.

### Bug 1 — logout after course payment — DIAGNOSED, NOT PATCHED (needs owner input)

**Confirmed real** from production auth logs (`unretire-prod`, read-only MCP, 2026-09-02): the owner's test user
logged in at 13:13:26, the course entitlement was written at 13:16:44, and the user **logged in again at
13:17:26** — 42 s later. After the Premium purchase (13:22:15) there was no re-login. So the course purchase did
lose the session and Premium did not.

**But:** there was **no `/logout` event and no `/token` error** for that user around the course purchase — the
session was not revoked server-side, it was simply **absent when the browser returned from Stripe**, so
`/account` ran `redirect("/login")`. And the course and premium checkout paths are **code-identical** apart from
Stripe `mode` (`payment` vs `subscription`) — nothing in the code deterministically logs a course buyer out and
not a premium one. The most likely cause is Supabase SSR session fragility across the cross-site Stripe redirect
(possibly a refresh-token rotation race, aggravated by `getUser()` running in middleware + layout + page), which
would bite intermittently rather than always-course. The parity **course** checkout test passes on Preview, so
it does **not** reproduce in the test environment — it is production-specific.

**Held deliberately.** Patching auth speculatively risks breaking the working Premium path. Pending: owner
confirms the exact symptom (bounced to /login vs "no access yet") and authorises the approach; then reproduce
before editing.

**Reproduction attempt 1 (2026-09-03, owner-authorised throwaway account, no payment) — did NOT reproduce.**
Drove a real browser (Chromium, agent-browser) against production: signed up fresh at
`/signup?intent=course`, which ran `register()` → `continueByIntent()` → `redirect()` straight to **live**
Stripe Checkout (`cs_live_…`, no card entered, no charge). Returned to `/account`: the session **survived** —
`sb-hcjivvlwxltyiycfbttc-auth-token` present, page rendered "Welcome back.", not bounced to `/login`. So the
leading hypothesis (a Server-Action external redirect dropping the just-set session cookie) is **disproven**,
alongside SameSite=Strict (cookies are Lax), the refresh race (1 h access token), a short cookie life (400 d),
and a server-side logout (no log event). The standard course flow does **not** log out in Chromium.

Throwaway account left in `unretire-prod` for the owner to delete: `claude.qa.s51c.1788379180@example.com`
(no entitlement; one abandoned live Checkout session, no charge).

**Reproduction attempt 2 (2026-09-03, completed-checkout return) — BLOCKED: the live coupon is invalid.**
Owner said the 100%-off coupon is `FREE` and the browser was likely iPhone/Safari. Logged in as the throwaway
account with `intent=course`, reached live Stripe, opened the promotion-code field and entered `FREE` — Stripe
returned **"This code is invalid."** So a $0 completion could not be exercised on the **live** account (the
coupon appears to be sandbox-only), and a real $99 charge is out of scope. No payment was submitted; browser
closed. **Launch-relevant finding:** the 100%-off coupon does not exist in **live** Stripe — this also affects
MN-003 (the post-launch live-purchase test, which planned to use it) and any "free access" promo.

**Why automation cannot settle this:** Playwright/agent-browser's WebKit is the open-source engine without
Apple's ITP, so it cannot replicate iPhone Safari's cross-site cookie behaviour; and the completed-checkout
return cannot be exercised on live without a valid coupon or a real charge. The one environment where the bug
occurs (the owner's device) is the one automation cannot reach. **Fastest path to a verdict: a ~2-minute
owner reproduction on the iPhone** with the steps in the report, capturing whether it lands on `/login`.

**Severity note:** even when the logout happens, the payment still succeeds and the entitlement is still
granted by the webhook (independent of the browser session) — the user simply has to log back in to reach the
content. It is a post-payment UX defect, not a money-loss or access-loss, and materially lower severity than
the worksheet 500 (which fully blocked a paid deliverable) that this sprint fixed.

**Remaining variables, and what would pin it:** (a) **browser/device** — Safari/iOS ITP partitions or drops
cross-site cookies on a redirect back from a third-party origin in ways Chromium does not; if the owner saw
this on Safari/iOS it would be browser-specific and invisible to a Chromium repro; (b) **the actual payment
completion** — this repro abandoned checkout; Stripe's real success redirect after a completed (or $0 coupon)
checkout was not exercised. Next step needs owner input: the browser/device they saw it on, plus either the
100%-off coupon code (to complete a $0 course checkout on prod and watch the return) or one owner-run repro
with devtools open (Network "preserve log" + Application → Cookies, and whether it lands on `/login`).
