## Two things this sprint got wrong

1. **PG-002 was written as one test crawling ten pages, then split into ten, then merged
   back into one.** The split was the wrong instinct applied from the right precedent: the
   26-route sweep in `public-pages.spec.ts` was correctly split because each route is
   independent, but these ten pages *share* a header and a footer, so per-page checking
   turned ~50 distinct routes into ~250 requests and made it worse. It is one deduped
   crawl with a documented budget, in a folder only one profile runs.
2. **Three form specs failed on the first run and the app was fine.** They navigated with
   `waitUntil: "domcontentloaded"` and clicked before React had hydrated, so the browser
   performed the form's native submission and no POST was ever issued. Diagnosed by
   probing rather than by guessing, which is the only reason it was not "fixed" by
   loosening the assertion.

## The first real CI run — what the new specs found, and what they broke

The suite ran against the deployed Preview for the first time at `0138cd6`:
**203 of 212 passed**, with nine failures in three groups. Two were my own defects and one
was the site's.

### 1. A test of mine sent real mail to the owner's inbox

`abuse/public-write-endpoints.spec.ts` fired three payloads it called "rejected". The third
— `{ form: "community", name: "E2E", email: "e2e@example.com", extra: 1 }` — supplies
**both** of `community`'s required fields with a well-formed address, so `/api/form`
accepted it, forwarded it to Formspree and answered **200**. A real "Community join
request" landed in the owner's inbox from CI, once per run.

The comment I wrote directly underneath it said the status "is a 400 only if something else
is missing". I wrote the doubt down and shipped it anyway, which is the same failure mode
as everything else this sprint is about. Two more were sent while reproducing it locally.

All three payloads are now invalid for a reason the route checks **before** its `fetch`, and
there is a structural backstop: the proxy answers `{"ok":true}` only when it has actually
forwarded a message, so the test now asserts that no payload in the list ever earns that.
It fails loudly rather than mailing someone.

That failure also aborted the serial describe, so the burst test and the subscribe test
never ran at all — the `-` marks in the run. They will now.

### 2. My route handler stripped the Preview bypass, so three forms never loaded

All three FM-005 tests timed out in `waitForHydration` on the Preview while passing locally.
The cause was not hydration:

`tests/e2e/fixtures.ts` registers a **context**-level route that attaches the Vercel
Protection Bypass header to same-origin requests. My spec registered a **page**-level
`route("**/*")` to watch for POSTs. Playwright runs the most recently registered handler
first, and `route.continue()` sends the request immediately, skipping every remaining
handler — so the bypass was never attached, Vercel answered 401 to the document itself,
React never hydrated, and the probe timed out with no clue why. `route.fallback()` passes
the request down the chain instead.

Localhost has no deployment protection, so none of this was observable in a local run. It is
the same blind spot that produced the S5.1a finding where the bypass never reached
API-style requests — re-introduced for browser requests, by me, in a spec written to catch
exactly this class of mistake.

### 3. Every Preview page advertised `http://localhost:3000` — Known issue 54

`PG-011` failed with `og:url` = `http://localhost:3000` **on the deployed Preview**.
`metadataBase` fell back to a localhost default because `NEXT_PUBLIC_SITE_URL` is a
build-time value on Vercel that is not scoped to the Preview environment. Production has it
and was unaffected, which is why it had never surfaced.

This is Known issue **19**'s failure mode — a deployment resolving its own URLs to
localhost — returning in a different environment, and it was invisible for exactly the
reason Finding 10 named: PG-011's only assertion sat inside an `if` that skipped when the
tag was missing, and it never looked at `og:url` at all. It failed within minutes of that
`if` being removed.

Fixed in `src/app/layout.tsx`: `metadataBase` now falls back to `https://$VERCEL_URL` — the
deployment's own platform-set hostname, the same identity `safe-origin.ts` trusts — before
it will consider localhost. A deployed build can no longer advertise localhost whatever the
environment variables say. Verified by rebuilding with `NEXT_PUBLIC_SITE_URL=""` and
`VERCEL_URL` set: `og:url` and `og:image` both resolve to the deployment origin.

## The money path, actually exercised — and what that cost to find

The point of making the checkout specs fail loudly was to find out whether the site can
take money. Four parity dispatches were needed to get an answer, and the answer was no —
twice for reasons nobody knew about.

| Run | Result | What it taught |
|---|---|---|
| 33413084944 | 13 failed | A Vercel-side transient: every session-bearing request 504'd from 16:17. Supabase's own logs show no errors and no rate limiting for that window — just traffic collapsing from ~61/min to 4–6/min. Not a code defect. |
| 33414598959 | 6 failed | **Premium bought successfully** — a real sandbox charge, the webhook, and a new entitlement row. The Course checkout reached Stripe and its card form never appeared. |
| 33416602782 | 7 failed | **Both** checkouts now failed *before* reaching Stripe, with no session created at all. This exposed Known issue **55**. |
| 33418400756 | 5 failed | **Both purchases passed** — Course in 17.5 s, Premium in 22.8 s, both writing real entitlement rows. The five remaining failures were a test-ordering race, fixed below. |

### Known issue 55 — two money-path bugs, found only because the specs stopped lying

Both were introduced by the review's Finding 5 fix, and both prevent a real customer paying.

**(a) The self-heal healed exactly once.** The key was `checkout:<user>:<product>:v2`; when
Stripe replayed a completed session the code created a replacement keyed `…:after:<A>` —
itself deterministic, so once that second session also completed the replay returned it
too. Verified directly against the sandbox: **every session whose status is not `open`
carries `url: null`** (17 of 17). The route therefore threw and answered 500, and a buyer
in that state could never pay again. Reproduced exactly — Premium bought at 16:34, and the
16:53 attempt created no session at all.

**(b) The key ignored the parameters.** `success_url`/`cancel_url` embed the request
origin, so the same buyer arriving from a different origin — a new Preview deployment, or
apex instead of www — reused the key with different parameters. Stripe rejects that
outright and checkout dies.

The key now fingerprints the exact parameters, so it identifies one operation *including
its inputs*; two tabs on one origin still share it, which is what Known issue 40 is about.
The self-heal is a bounded loop chaining on each stale session's distinct id.

### The ordering defect this exposed in the suite itself

With the fixtures cleared, five entitled-member specs failed — `roles-chromium` runs
concurrently with `parity-chromium`, and the purchases that make the fixtures entitled had
not landed yet. Invisible while the fixture accounts permanently owned their products, and
a guaranteed failure the moment they did not.

It also meant the parity suite could not be green in **either** direction: leave the
fixtures owning their products and the checkout specs correctly refuse to report a purchase
they did not make; clear them and five specs race the purchase and lose. `roles-chromium`
now depends on `parity-chromium` when parity is enabled — the same remedy, and the same
reasoning, as `logout-chromium` depending on `roles-chromium`. An ordering fix, not a
weakened assertion.
