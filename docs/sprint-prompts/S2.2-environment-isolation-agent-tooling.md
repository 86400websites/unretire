## Context at planning time

Planning was done by reading the governing docs end to end (`docs/ROADMAP.md` S2.2 row, `docs/ENVIRONMENT-PARITY.md`
§§2–9, `docs/SUPABASE-MCP-SAFETY.md`, `docs/OWNER-ACTIONS.md`, `docs/PROJECT-STATUS.md` §§4–10) and by reading
the code that consumes environment variables. Findings that shape this sprint:

1. **No `src/` change is required, and this was verified mechanically, not assumed.** All 18 `process.env`
   reads use literal, environment-independent names; nothing branches on `VERCEL_ENV`/`NODE_ENV`; there is no
   `.env` loading logic and `next.config.ts` declares no `env` block. Every provider read is lazy and
   in-request (`src/app/api/subscribe/route.ts:10-13`, `src/lib/stripe/server.ts:13-21`,
   `src/lib/stripe/checkout.ts:13,18,38`, the Supabase factories), and both origin-deciding paths already
   prefer the live request over env (`src/app/api/checkout/route.ts:31-34`, `src/app/auth/actions.ts:19-26`).
   Vercel's per-environment scoping of the same names **is** the separation mechanism.
2. **`NEXT_PUBLIC_*` values are inlined at build time**, so every variable change needs a **redeploy** before
   it is true of a running deployment. This is the most commonly skipped step (`docs/ENV-VARS-SAFETY.md`).
3. **Two governing-doc conflicts were found and are NOT resolved silently** — they are Open decisions
   **D-20** and **D-21** in `docs/PROJECT-STATUS.md` §8, and Gate 0 below will not pass without them.
4. **Formspree cannot be isolated by env alone.** `src/app/contact/ContactForm.tsx:5` and
   `src/app/community/CommunityJoinForm.tsx:5` hardcode the endpoint with no env read;
   `src/app/enterprise/DiscoveryForm.tsx:16-18` reads `NEXT_PUBLIC_FORMSPREE_ENDPOINT` but **falls open to the
   live endpoint** when unset. `docs/ENVIRONMENT-PARITY.md` already records this as an accepted
   non-isolation. This sprint re-documents it; it does not fix it (a code change belongs to its own sprint).
5. **The webhook mixes two providers.** `src/app/api/stripe/webhook/route.ts` verifies with
   `STRIPE_WEBHOOK_SECRET` and then writes entitlements through `SUPABASE_SECRET_KEY`
   (`src/lib/supabase/admin.ts:12`). Split one without the other and a Sandbox payment writes into
   `unretire-prod` — **silently**, because neither the upsert nor the cancel update inspects `.error`
   (Known issue 22, S3.1). The Supabase and Stripe Preview values must move together; they already have.
